# Releasing openPedal

The desktop app and the iPad app are released separately, each with its own version,
tag and changelog. The shared core (DSP, graph, engine, server) goes into both.

## Products

| Product | Version source | Tag | Changelog | Installed with |
|---|---|---|---|---|
| Desktop (binary + web UI) | `[workspace.package] version` in `Cargo.toml` | `desktop-vX.Y.Z` | `apps/desktop/CHANGELOG.md` | `cargo build --release` |
| iPad app | `CFBundleShortVersionString` in `apps/ios/Info.plist`, plus `CFBundleVersion` (build number, +1 on every release, dev ones too) | `ios-vX.Y.Z` | `apps/ios/CHANGELOG.md` | xtool, see below |

The protocol version (`PROTOCOL_VERSION`, the `protocol` field in `state`) is not a product.
Bump it when a change breaks the protocol between the core and the UI, so an older client
cannot talk to a newer core (or the other way round). Mark that commit with a
`BREAKING CHANGE: protocol vN` footer (or a `!` after the type): git-cliff then lists it under
"Breaking changes" in both changelogs.

## Changelogs

`apps/desktop/CHANGELOG.md` and `apps/ios/CHANGELOG.md` are generated by [git-cliff](https://git-cliff.org) from
the Conventional Commits. Do not edit them by hand. `tools/release.sh` regenerates the changelog
of the product being released, with the new version on the commits since the last stable tag (stable releases only).
Configuration: `cliff.toml`.

Commit messages must be `type(scope): summary`, in English (see `CONTRIBUTING.md`). Only
`feat`, `fix`, `perf`, `refactor`, `docs` and breaking changes reach a changelog, grouped as
Features, Fixes, Performance, Refactor and Documentation. Older commits (Italian, not
conventional) are left out.

### Scope routing

| Scope | Desktop changelog | iPad changelog |
|---|:-:|:-:|
| `ui` | yes | no |
| `ios` | no | yes |
| `dsp`, `graph`, `engine`, `server`, `ffi` | yes | yes |
| `docs`, `nix`, `chore` | no | no |
| no scope, or other scopes | yes | yes |

Commits of types `test`, `build` and other unlisted types are never in a changelog. Release
commits (`chore(release): ...`) are skipped as well.

## Branches and tags

| Branch | Purpose | Branch from | Merge into | Tags |
|---|---|---|---|---|
| `master` | stable only | | | `desktop-vX.Y.Z`, `ios-vX.Y.Z` |
| `dev` | integration and testing | | `master` (`--no-ff`, only to cut a stable release) | `desktop-vX.Y.Z-dev.N`, `ios-vX.Y.Z-dev.N` |
| `feat/*`, `fix/*`, `chore/*`, `docs/*` | one change | `dev` | `dev` (`--no-ff`) | none |
| `fix/*` hotfix | urgent fix of a stable release | `master` | `master`, then back into `dev` | stable tag |

In a dev tag, `X.Y.Z` is the upcoming stable version and `N` starts at 1 and counts up for
each `X.Y.Z`. Dev tags never split the stable changelog: a stable release lists everything
since the previous stable tag (`cliff.toml` ignores `-dev.N` tags).

Versions of a dev release:

- desktop: the full string, e.g. `0.3.0-dev.2`, in `[workspace.package] version`;
- iPad: `CFBundleShortVersionString` stays numeric (`0.3.0`, Apple requires it) and only
  `CFBundleVersion` (the build number) tells builds apart. It goes up on every release, dev included.

## Cutting a release

The script never pushes. `--dry-run` shows what would happen and changes nothing; a wrong
branch or a dirty tree is then only a warning.

### Dev pre-release (on `dev`, clean tree)

```sh
tools/release.sh desktop next-dev --dry-run  # next -dev.N of the upcoming version
tools/release.sh desktop next-dev            # checks, version bump, commit, tag
git push origin dev desktop-v0.3.0-dev.1     # you push
```

`next-dev` takes the minor after the latest stable tag (0.2.0 -> 0.3.0), or continues the
dev series already in progress. For another version: `tools/release.sh desktop 1.0.0-dev`
(next N for 1.0.0) or an exact `1.0.0-dev.3`. Same for `ios`. The changelog is not touched;
the commit is `chore(release): desktop v0.3.0-dev.1`.

### Stable release (on `master`)

```sh
git checkout master
git merge --no-ff dev                        # all the work to ship
tools/release.sh desktop 0.3.0 --dry-run
tools/release.sh desktop 0.3.0               # checks, version bump, changelog, commit, tag
git push origin master desktop-v0.3.0        # you push
git checkout dev && git merge master         # bring the release commit back into dev
git push origin dev
```

Replace `desktop` with `ios` for the iPad app (each product is released on its own).

### Hotfix

```sh
git checkout -b fix/short-name master
# fix, test, commit
git checkout master && git merge --no-ff fix/short-name
tools/release.sh desktop 0.3.1               # on master
git push origin master desktop-v0.3.1
git checkout dev && git merge master         # the fix must reach dev too
```

### What the script does

1. checks the version: `X.Y.Z` only on `master`, `X.Y.Z-dev.N` only on `dev`; that the tree
   has no uncommitted changes (untracked files are ignored) and that the tag does not exist yet;
2. runs the checks: desktop: `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`,
   `npm run build` in `apps/desktop/ui/`; iPad: `cargo test --workspace`, `apps/ios/scripts/build-core.sh`,
   `apps/ios/scripts/xtool.sh dev build`. `--skip-checks` skips them;
3. bumps the version (and refreshes `Cargo.lock` for the desktop);
4. stable only: regenerates the changelog of that product;
5. commits `chore(release): desktop vVERSION` (or `ios vVERSION`) and creates the annotated tag.

## Installing the iPad release

Check out the tag (`git checkout ios-v0.1.0`, or a dev tag to try a pre-release), then follow `apps/ios/README.md`, section
"Build with xtool": `nix develop -c apps/ios/scripts/build-core.sh` and `apps/ios/scripts/xtool.sh dev`
with the iPad connected and unlocked. Free Apple IDs sign the app for 7 days.

## Tags

Tags are annotated and never moved or reused. If a release is wrong, fix forward with a new
version.
